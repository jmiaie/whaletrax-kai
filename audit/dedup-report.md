# Whaletrax Deduplication Audit Report

## Overview
An audit of the Whaletrax and WalletHound codebases was performed to identify redundant logic, copy-pasted functions, and unnecessary abstractions.

## Findings

### 1. Model Duplication: `WalletStats` vs `HoundResult`
- **Location:** `src/models.py:53` vs `src/wallethound/models.py:91`
- **What it does:** Both classes aggregate wallet-level statistics (profit, volume, trade counts, win rates, etc.).
- **Why it's duplicated:** `HoundResult` was likely created to add specialized fields for the `wallethound` module, but it repeats almost all fields from `WalletStats`.
- **Confidence:** **High**
- **Recommendation:** `HoundResult` should inherit from `WalletStats` or be merged. Since `HoundResult` is used for more complex analysis, having it as a subclass of `WalletStats` reduces field redundancy.

### 2. Leaderboard Parsing Logic
- **Location:** `src/wallet_scanner.py:23` (`_parse_leaderboard_entry`) and `src/wallethound/scanner.py:10` (imports and uses it).
- **What it does:** Converts raw JSON from the Polymarket API into a structured `LeaderboardEntry`.
- **Why it's duplicated:** While the function itself is in `src/wallet_scanner.py`, both `scan_leaderboard` (in `src/wallet_scanner.py`) and `hound_leaderboard` (in `src/wallethound/scanner.py`) contain near-identical loops that call `pm.get_leaderboard`, loop through results, and call `_parse_leaderboard_entry`.
- **Confidence:** **High**
- **Recommendation:** Consolidate the leaderboard fetching and entry parsing into a single generator or helper in `src/polymarket_client.py` or a dedicated parser module.

### 3. Display Helpers and Formatting
- **Location:** `src/display.py:19-45` vs `src/wallethound/display.py:13` (imports them).
- **What it does:** Formatting functions like `_fmt_usdc`, `_fmt_pct`, and `_profit_style`.
- **Why it's duplicated:** They were originally private (`_`) in `src/display.py`. `wallethound/display.py` imports them, but the duplication is in the *UI pattern* of the tables.
- **Confidence:** **Medium**
- **Recommendation:** These helpers are already partially shared via import, but they should be made public (remove `_` prefix) and centralized in a common `ui_utils.py` or similar if they grow.

### 4. Raw API Field Mapping (`_safe_float` and field dict lookups)
- **Location:** `src/wallet_scanner.py:14`, `src/wallet_scanner.py:30` (`_parse_trade`), `src/wallet_scanner.py:65` (`_parse_position`), `src/wallet_scanner.py:118` (`_enrich_stats_from_closed_positions`).
- **What it does:** Defensive code to handle multiple possible field names from Polymarket's inconsistent API (e.g., `raw.get("market") or raw.get("marketId")`).
- **Why it's duplicated:** This defensive mapping is scattered across multiple parsing functions.
- **Confidence:** **High**
- **Recommendation:** Create a unified `Mapping` or `Resolver` utility that takes a raw dict and a list of keys and returns the first found value, or better, centralize the "normalization" step before it reaches the models.

## Implementation Plan (High Confidence Only)

1. **Refactor Models:** Modify `src/wallethound/models.py` so `HoundResult` inherits from `WalletStats`.
2. **Unified Parsing:** Move `_safe_float` and `_parse_leaderboard_entry` to a more central location or ensure they are used consistently.
3. **Clean up `src/wallethound/scanner.py`:** Use the refined models and shared parsing.
